1. Что РЕАЛЬНО сломано/уязвимо (проверено построчно)
🔴 P0-A. Telegram-бот — записи в БД не работают вообще (Audit1 прав)
8× синхронный db.commit() (telegram_bot.py:881, 938, 959, 987, 1177, 1234, 1382, 1445) на AsyncSession из get_db_context() — возвращается и отбрасывается корутина, ни одна запись не сохраняется.
Все мутации идут в эфемерный dict из _build_data_dict(): создание/удаление/блокировка пользователей, /addserver, установка/удаление протоколов (контейнер на сервере ставится, запись в БД — нет).
/addserver крашится: data.setdefault("servers", []).append(...) — servers это dict → AttributeError. Та же ошибка в _admin_create_client: data.setdefault("user_connections", []).append(...).
SSH-креды не расшифровываются: _get_ssh_and_manager (стр. 414) передаёт сырой s.password (Fernet v1:...) в SSHManager, в отличие от app.get_ssh(), который вызывает decrypt_secret(). Все серверы, добавленные через веб-панель, из бота не подключаются.
_admin_remove_client удаляет клиента на сервере, но не удаляет строку Connection из БД → сироты.
Уточнение к Audit1 #4: «разрушает структуру данных» — преувеличение (dict эфемерный); суть верна: операция не работает.
🔴 P0-B. Веб-API: управление пользователями сломано (оба аудита правы)
perform_delete_user(data: dict, ...) / perform_toggle_user (app.py:1159, 1182) вызываются с AsyncSession вместо dict (routers/users.py:242, 259, 274) → TypeError на data['users']. Удаление и блокировка пользователя через панель не работают.
api_add_user / api_delete_user / api_toggle_user используют get_current_user (только cookie), а не _check_admin (cookie + Bearer) → API-токены на этих трёх роутах игнорируются.
🔴 P0-C. Инъекции команд на управляемых серверах (Audit1 прав, и даже мягче, чем есть)
telemt_manager.py:56-57: json.dumps(data).replace('"', '\\"') и вставка в curl -d "..." под sudo. $(), backticks не экранируются. user_ad_tag/secret/имя клиента приходят из пользовательского ввода (AddUserRequest.telemt_ad_tag) → RCE на удалённом сервере.
Порт — строка без валидации: InstallProtocolRequest.port: str = '55424' (routers/protocols.py:24) передаётся как есть в docker run -p {port}:{port}/udp (wireguard:207, xray:336) и т.д. int(req.port) вызывается только при записи в БД, после исполнения shell. Audit1 писал «если роутер пропустит» — роутер реально пропускает.
🔴 P0-D. Нашёл сам — ни один аудит не заметил
UserConnection.id не имеет default (ни в модели, ни в миграции), при этом models.Connection(...) создаётся без id в routers/users.py:190, 327 и routers/connections.py:133 → INSERT падает с NOT NULL constraint. Создание подключения с привязкой к пользователю сломано во всех трёх местах. Корректно только в app.py:1274 (там id=str(uuid.uuid4())). Тестами не покрыто.
