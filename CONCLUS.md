# Аудит проекта — выводы

Дата аудита: 2026-11-03. Снимок рабочего дерева, все находки воспроизводимы командами (`pytest --cov`, `wc -l`, `grep`). Проверено и уточнено 2026-11-04: числа сверены с кодом, расхождения исправлены.

**Общая оценка: 7/10** — крепкая локальная разработка. Тесты зелёные (118 passed), практики безопасности реально реализованы, документация (AGENTS.md, docs/terrain/) в порядке. Главные долги: непокрытые тестами менеджеры протоколов, бог-объект app.py, frontend-монолиты в шаблонах.

## Сильные стороны

- 118 тестов проходят; HTTP-слой тестируется через TestClient, SSH мокается на границе router↔хост (правильное место).
- Покрытие helpers/secrets/models/amnezia_config — 90%+.
- Безопасность на месте и подтверждена кодом: Fernet для credentials, SHA-256 digest API-токенов, TOFU host key pinning, sudo-пароль через stdin, `shlex.quote` для путей, CSRF.
- SSH-операции корректно убраны в потоки: синхронная работа завёрнута в `asyncio.to_thread` (119 использований в 8 файлах), унифицированный `get_ssh`, в backup-эндпоинтах `try/finally`. Основные SSH/процесс-операции не блокируют event loop (полной гарантии без аудита каждого синхронного вызова нет).
- PBKDF2 везде 600k итераций (app.py и database/repositories.py).
- Миграции alembic (3 версии), слоистая структура routers/managers/database.

## Проблемы

### 1. Покрытие тестами инвертировано по риску (главная)
Общее покрытие ~24%, но ядро продукта практически без тестов:
- awg_manager 13%, wireguard_manager 13%, xray_manager 16%, ssh_manager 17%
- telemt/nginx/socks5/adguard managers — 0% (также dns 0%, backup 18%)
- telegram_bot.py — 11%
- роутеры — 18–56% (auth.py 56%, остальные до 43%)

Тестированы auth/helpers (90%+), а логика развёртывания Docker на удалённых серверах — самая аварийно-опасная часть — без тестов.

**Как исправить:**
- Начать с чистых функций менеджеров: генерация конфигов, парсинг вывода SSH, построение docker-compose — тестируются без моков сети.
- Для SSH-вызовов — фейковый SSHManager (записывает команды, отдаёт fixture-вывод); уже есть моки в tests/conftest.py, распространить на менеджеров.
- Цель не «80% всего», а покрытие критических веток: install/remove, add/remove client, sync traffic.
- Образец уже в проекте: amnezia_config.py покрыт на 94% именно как чистый генератор конфигов — по такому же шаблону тестировать генерацию конфигов в xray/awg.
- После наращивания покрытия зафиксировать пол: `fail_under` в конфиге coverage (или `--cov-fail-under` в pytest), иначе без механического контроля покрытие снова поплывёт вниз.

### 2. app.py — бог-объект
2251 строка, 75 функций (71 top-level). В одном файле: реестр протоколов, фабрика менеджеров, туннели (cloudflared, ~400 строк процесс-менеджмента), WARP, хеширование паролей, генерация токенов, background jobs. Кандидаты на вынос: tunnels, protocol registry.

**Как исправить:**
- Поэтапно: сначала `managers/tunnel_manager.py` (туннели + WARP, строки ~324–970, ~645 строк, слабо связаны с остальным), затем `protocols/registry.py` (protocol_base/key/display_name/container_name + factory).
- Третий шаг: auth/token helpers (`hash_password`, `verify_password`, `_hash_api_token`, генерация токенов) — заодно закрывает проблему №4 (см. там про целевой модуль).
- После каждого выноса оставить в app.py тонкие обёртки под старыми именами — не ломать `import app as app_module` (см. границы в AGENTS.md).
- Критерий готовности: app.py < 1000 строк. Учесть арифметику: вынос туннелей (~645) и registry (~100) даст ~1500 строк — без третьего шага (и, возможно, выноса background jobs) до цели не дойти.

### 3. Frontend — монолиты в шаблонах
- server.html — 2231 строка, users.html — 1097, settings.html — 985
- Весь JS инлайновый, без сборки и линтинга; состояние UI сложно синхронизировать с сервером.

**Как исправить:**
- Минимум: вынести инлайн-JS из шаблонов в static/js/*.js по страницам (server.js, users.js) — шаблон оставить разметкой. Это включает кеширование и позволяет линтить.
- Главная практическая сложность: инлайн-JS использует Jinja-переменные (переводы, CSRF-токен, данные сервера). При выносе нужен механизм передачи данных в скрипт — `data-*` атрибуты или один блок `window.APP_CONFIG = {...}` в шаблоне. Без этого план упрётся в первый же шаблон.
- Дальше по желанию: выделить повторяющиеся виджеты (client list, traffic chart) в функции/компоненты без фреймворка; полный фронтенд-стек (Vue/React) для этого проекта — overkill.

### 4. Дублирование логики между слоями
- `hash_password` в двух местах: app.py и database/repositories.py (итерации совпадают, дубль остался).
- Бизнес-логика (scrape трафика, получение конфигов, SSH-хелперы) продублирована между routers/* и telegram_bot.py (1682 строки) — правка в одном месте забывается во втором.

**Как исправить:**
- `hash_password`/`verify_password` — перенести обе функции в `database/repositories.py` (там уже лежит копия, `scripts/manage_users.py` импортирует именно оттуда; `verify_password` живёт только в app.py и переедет туда же). В app.py оставить тонкие обёртки: `app_module.hash_password` используется в routers/users.py, routers/sharing.py, telegram_bot.py — ломать нельзя.
- Общие сценарии (получить SSH+manager, скачать конфиг клиента, scrape трафика) вынести в service-функции (например, `services/connections.py`), чтобы и роутеры, и telegram_bot вызывали одно и то же.

### 5. Два стиля доступа к данным
Repositories (database/repositories.py) и прямые SQLAlchemy-запросы в роутерах сосуществуют. Инварианты БД размазаны, не зафиксированы в одном месте.

**Как исправить:**
- Постепенно переносить прямые запросы из роутеров в repositories; новый код — только через repository.
- Не делать большой рефакторинг «в лоб»: по одному роутеру за раз, тесты подтверждают поведение.

### 6. Нет механического контроля качества
- Нет ruff/flake8/black/mypy в конфигах.
- ~190 except-блоков, ~46 мест `except: pass` (часть — легитимные probe-паттерны, но без линтера неотличимы от проглоченных ошибок).
- scratch_test.py, scratch_test2.py закоммичены в корне — мусор.

**Как исправить:**
- `venv/bin/pip install ruff` (по AGENTS.md — только через venv), конфиг `pyproject.toml` (line-length, ignore-список под проект), прогон по всему коду; ruff добавить в dev-зависимости, а не ставить ad-hoc.
- Пройтись по ~46 местам `except: pass`: где probe-паттерн — оставить с комментарием, где ошибка глотается — добавить логирование.
- scratch-файлы — удалить из git (`git rm --cached` + в .gitignore, если нужны локально; иначе просто `git rm`).

### 7. Протокольные менеджеры без единого интерфейса
Сигнатуры исторически различаются; `_manager_call` специально обрабатывает WireGuard. Признано в AGENTS.md, но удорожает добавление нового протокола.

**Как исправить:**
- Не делать большую унификацию сейчас (рискованно, трогает все протоколы сразу).
- Вариант «дешевле»: зафиксировать в AGENTS.md/terrain минимальный обязательный набор методов менеджера (контракт «как у WireGuard») и проверять новые менеджеры по нему; унификацию делать только при добавлении следующего протокола.

### 8. Артефакты закоммичены в репозиторий
- `app.db` (SQLite, ~64K) отслеживается в git и отсутствует в .gitignore — пользовательские данные в VCS, источник конфликтов и рассинхрона состояния.
- `bin/cloudflared` — бинарник на 38 МБ в git. При этом в app.py уже есть механизм скачивания (`get_tunnel_download`/`install_tunnel_binary`), хранить бинарник в репозитории не нужно.

**Как исправить:**
- `app.db`: добавить в .gitignore + `git rm --cached app.db`.
- `bin/cloudflared`: `git rm --cached` + `bin/` в .gitignore (скрипт установки скачает бинарник на целевой машине). Полная очистка истории (filter-repo) — опционально, отдельной задачей.

## Приоритеты действий

1. Тесты на менеджеров протоколов — начать с чистых функций (генерация конфигов, парсинг ответов SSH), не требующих сетевых моков.
2. Вынести tunnels и protocol registry из app.py.
3. Подключить ruff (одна команда, мгновенный выигрыш).
4. Свести `hash_password` и SSH-хелперы к одному источнику.
5. Убрать из репозитория scratch-файлы, `app.db` и `bin/cloudflared` (git rm --cached + .gitignore).
